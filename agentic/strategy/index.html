    Agentic workflow strategy

    This repository — a deliberately vulnerable Django teaching app (Insecure Bank Corp) — uses GitHub Agentic Workflows (gh aw) to run a small, label-driven issue pipeline. This document describes how the pieces fit together.

    The pipeline

    issue opened/reopened ──▶  AW - Triage   ──(applies label)──▶  AW - Launcher  ──▶ draft PR + comment
                          (triage.md)                          (launcher.md)
    1. Triage (.github/workflows/triage.md) runs on issues: [opened, reopened] (and manual workflow_dispatch). It classifies the issue, applies labels, and posts one guidance comment. It never edits code. Issue text is treated strictly as untrusted data.
    2. Launcher (.github/workflows/launcher.md) runs when the enhancement or security label is applied (and manual workflow_dispatch). It is thin orchestration: it picks the path from the label and delegates the engineering work to the issue-engineer sub-agent, which writes real, working code, adds/updates tests, and opens a detailed draft PR under the ai/ branch prefix, then comments a link. It only ever runs the path named by the applied label.

    The compiled *.lock.yml files next to each *.md are generated by gh aw compile — never edit them by hand. After changing a .md, run gh aw compile and commit both files.

    Labels

    The launcher reacts only to two labels; the full vocabulary is owned by triage's add-labels.allowed list and provisioned by the create_labels operation in agentics-maintenance.yml (there is no static labels YAML):

    Label Meaning Drives launcher?
    agentic-workflow Applied to every triaged issue no
    security Reports a vulnerability/weakness yes → security path
    severity:critical\|high\|medium\|low Severity of a security issue no
    enhancement Feature request / improvement yes → enhancement path
    bug, documentation, question, triage Other categories no
    ai-generated, needs-review Applied by the launcher to its draft PRs no

    Only enhancement and security invoke the agent — the launcher's on.issues.names filter makes any other labeling event show as Skipped rather than spending an agent run.

    Safe-outputs contract

    Agentic workflows never push directly; every side effect goes through a declared safe-outputs:

    Workflow Safe outputs
    Triage add-comment (max 1), add-labels (max 3, from the allow-list), noop
    Launcher add-comment (max 1), create-pull-request (draft, branch-prefix ai/, labels ai-generated+needs-review), noop

    The launcher's create-pull-request may modify any file the change needs (app code, tests, docs, and config/build files such as Dockerfile, compose.yml, or pyproject.toml) but cannot touch .github/** (CI, workflows, rulesets) — enforced by the !.github/** exclusion plus gh-aw's default protect_top_level_dot_folders guard. It is also gated by roles: [admin, maintainer, write], so only trusted collaborators can drive the code-writing agent by applying a label.

    The launcher produces real fixes

    The launcher implements the actual change — not stubs or documentation-only PRs. For an enhancement it builds the feature through the existing service/model layers; for a security issue it remediates the vulnerability in code and documents the CWE, severity, root cause, exploitation, and the exact fix in the PR body.

    The vulnerabilities in this app are intentional teaching artifacts, and the suite under tests/security/ asserts that they still exist. Because a real fix changes that behaviour, the launcher updates the corresponding tests/security/ test(s) to assert the fixed behaviour (e.g. that an injection payload is now rejected), so the suite and the --cov-fail-under=92 coverage gate stay green. The security scenarios themselves are documented in docs/security/ (scenario-1.md … scenario-6.md).

    The launcher is not a vulnerability scanner: Snyk owns SAST/SCA and Dependabot owns dependency updates. A security issue describes an already-identified finding, and the launcher's scope is in-code remediation only — it does not bump dependencies or edit pyproject.toml/uv.lock/ requirements.txt for a version fix. If a finding can only be resolved by a dependency bump, the launcher notes that and defers to Dependabot.

    Sub-agent and skills

    The engineering knowledge lives in a reusable sub-agent and three skills, not in the launcher prompt. gh-aw stages everything under .github/agents/ and .github/skills/ into the runtime (via the activation artifact and the restore_inline_sub_agents.sh / restore_inline_skills.sh steps in launcher.lock.yml), so the Copilot engine can discover and invoke them — the launcher only references them by name.

    These resources are written repo-agnostic — they carry no IBC/Django/tooling specifics — so the same sub-agent and skills can be reused across repositories; repo specifics are discovered at runtime.

    • .github/agents/issue-engineer.md — the senior-engineer sub-agent the launcher delegates to. It implements the fix/feature and authors the PR, using the skills below.
    • .github/skills/codebase-grounding/ — a method for deriving a repo's architecture, conventions, commands, and test layout from its own config (README/CONTRIBUTING, .github/copilot-instructions.md, package manifests) rather than hardcoding them.
    • .github/skills/resolve-issue-pr/ — the fix-to-PR procedure and the PR quality bar.
    • .github/skills/security-remediation/ — how to remediate a known finding in code, with a CWE→fix-pattern reference and the code-only scope described above.

    Related configuration

    • .github/copilot-instructions.md — repo conventions (uv, pytest, ruff line-length 128, PEP 257).
    • agentics-maintenance.yml — scheduled/manual maintenance (label creation, safe-output cleanup, enable/disable/upgrade of agentic workflows).
    • .github/aw/actions-lock.json — pinned gh aw action/container versions.
